Engineering insight · In development

roleNaviq: Designing clear responsibilities

The priority is not feature volume, but clear boundaries between the interface, server state and security logic.

Decision 01

Server state is not local UI state

TanStack Query owns API loading, caching and synchronisation. React Hook Form and Zod handle form state and validation. This avoids creating a second client-side data source that must be kept in sync manually.

Decision 02

The API is the security boundary

JWTs are stored in HttpOnly cookies. Protected frontend routes improve the user experience, but they are not an authorisation layer: the server also verifies resource ownership for every application request.

Trade-off

A flexible data model with controlled structure

MongoDB supports incremental changes to the application model, while Mongoose keeps document structure explicit. More complex analytics are deliberately deferred until the product requirements justify them.

Next quality gate

Secure the foundation before adding intelligence

Before a public demo, the next step is to add API and component tests, critical Cypress journeys, axe-core accessibility checks and CI. Planned AI capabilities will then be introduced as a clearly separated extension.

Status: active development
Engineering insight · Master's thesis

Creating a fair SPA, SSR and SSG comparison

The real challenge was not building three shops. It was controlling the variables so that the rendering strategy remained the meaningful difference.

Comparison design

The same task, delivered differently

The data model, core functionality and product scope were kept as consistent as possible. This made it easier to attribute differences to rendering rather than unrelated product features.

Trade-off

Computation moves; it does not disappear

An SPA moves more work into the browser, SSR renders at request time and SSG spends that effort during the build. The right choice therefore depends on freshness requirements, infrastructure and usage patterns.

Measurement approach

Measure initial load, navigation and updates separately

A single metric would be misleading. The comparison becomes more useful when initial load, subsequent navigation, SEO requirements and update effort are evaluated independently.

Key lesson

There is no universal winner

Rendering is an architectural decision with competing priorities. The main lesson was learning to evaluate those trade-offs in the context of a specific product.

Engineering insight · Full Stack

Tour World: Trust stops at the browser

For accounts and bookings, the interface must feel responsive while authorisation and business-critical decisions remain on the server.

System boundary

Client actions are requests, not proof

The browser initiates sign-in, reviews and checkout. Whether an action is permitted must still be decided on the server using the authenticated identity and role.

Architecture

One connected request flow

The server-rendered application exposed the complete path from route and controller through the data model and template to the response. This made the dependencies between frontend and backend explicit.

Error strategy

Handle errors where the context exists

Validation, authorisation and external services require different responses. Centralised error handling provides consistency without hiding the underlying domain cause.

What I would improve today

Modernise and test critical boundaries

I would update dependencies, validate environment variables strictly, isolate payment logic behind a service and cover authentication and booking flows with integration tests.

Engineering insight · Frontend

Recipe App: Keeping change local

The central question was how to add views and interactions without spreading API access and DOM logic throughout the application.

Structure

One responsibility per module

The model owns data and application state, views handle rendering and UI events, and the controller coordinates the two. Changes therefore stay closer to the responsibility that caused them.

Data flow

A traceable source of UI state

Search results, serving sizes and bookmarks are derived from one central state. The interface renders that state instead of maintaining parallel copies in several places.

Trade-off

Vanilla JavaScript makes architecture visible

Without a framework, rendering, events and state changes must be organised explicitly. This requires more initial effort, but exposes the mechanics behind component-based frameworks.

What I would improve today

Modernise dependencies and quality controls

I would modernise the build dependencies, add tests for state transitions and systematically review loading, error and keyboard states while retaining the existing MVC structure.
